### 3.1 判定与实现路线（`M8-13` 的前置选择 · **待用户拍板**）

> ✅ **已拍板（2026-10-06）：① / ② / ③ 的提问已作废** —— 用户选择**模板化**方向（= ② 的**进程内**形态，
> 但**不**把它当作「CDP 端点」使用、也**不**投入 ① 的 native 复刻）。下表**保留原文**作为决策依据与历史。
> * 走的是 **②「WebView2 复用站点 SDK」** 的实质：文件注入用**进程内** `CallDevToolsProtocolMethod`（`DOM.setFileInputFiles`），签名与直传交给**页面内官方 SDK**；
> * 与 ② 的差别：**不是**「POC 探索」而是**模板化的核心路径**（每站一个独立上传单元）；**不是**远程调试端点 ⇒ 不违反 `M7.md` `D5`（术语订正见 `M7.md` `D5` 行与本文 §13.4）；
> * ①（native HTTP 复刻 `s=`）**本轮不做**；`M8-13` 的「C++ 原生上传 POC」**关闭**（由 §13 的模板取代）。


**已确立的契约（源码级 + 物证）**：

```
① ResourcePrepareUpload（alice API · Cookie + device_id 查询参数）
     ⇒ 响应 data 含：upload_host · service_id(= a9rns2rl98) · upload_auth_token{access_key, secret_key, session_token, current_time, expired_time}
② ApplyImageUpload   → ③ TOS 直传(PUT/POST 到 UploadHost/StoreUri) → ④ CommitImageUpload（带 ② 下发的 SessionKey）
```

| 路线 | 做法 | 优 | 劣 |
|---|---|---|---|
| **① 纯 native（原方案 E）** | C++ 用会话 Cookie 调 ①，再**在 C++ 里复刻 `s` 短签名** + ②③④ | 无浏览器脚本参与；「原生 HTTP」纯度最高 | **必须拿到 SDK 的签名算法**（`lHg` 模块在 1001 分包之一，已试 34 个未命中）⇒ 需继续 crawl 或实测比对；**抗改版 ≈ 0**（`R1`） |
| **② WebView2 混合（推荐先做 POC）** | C++ 读文件 + 驱动流程；**文件注入用 CDP `DOM.setFileInputFiles`**，签名与直传交给**页面内的官方 SDK**（即真人拖文件的等价物） | 零 Python / 零 IPC；**复用站点 SDK ⇒ 抗改版最好**；真机一步到位 | 把 **CDP 纳入核心路径** ⇒ 需**订正 `M7.md` `D5`**（「不使用 WebView2 CDP 端点」）；上传字节走页面 JS（仍为浏览器原生 HTTPS） |
| **③ 先补 crawl 再回 ①** | 继续在 1001 分包里定位 `lHg`（ImageX SDK），读清 `s` 算法后再实现 | 拿到 ① 的前提 | 成本不确定（分包体积大、命中率低，已试 34 个为 0） |

> **本里程碑建议**：先走 **②** 拿到 Phase 2 Gate 的双证（`both=true`，证明链路真的能通），再按 `M8-Q2`（合规口径）与用户时间决定是否投入 **①**（纯 native）。两者不冲突：② 的实现可作为 `adapter=dom` 的**上传兜底**长期保留（正是 `R2` 要求的双轨）。

| 函数指针 | 语义 | 站点单元要回答的问题 |
|---|---|---|
| `prepare(local_path, options, → out_path/note/error)` | **准备**：要不要转码/缩放 | 「我的白名单 / 体积 / 边长限额是什么？」 |
| `deliver(plan, paths, → detail/error)` | **交件**：怎么把文件交给页面 | 「文件输入框选择器是什么？要不要先点按钮？」 |
| `expect(site) → UploadExpectations` | **判据**：算不算交付成功 | 「页面哪个节点出现？哪条网络请求说明真发了？」 |
| `prepare_options(site) → UploadPrepareOptions` | **默认准备参数**（表字段可覆盖） | 「我默认接受哪些格式 / 目标格式 / 长边上限？」 |

> 关键取舍：**站点知识的权威在站点单元代码里**；配置表只做「**选哪个单元 + 可覆盖项**」⇒
> 换 DOM 时改表即可（不动代码），换站点时加一个 `.cpp`（不动引擎）。

### 13.3 接入一个新站点 = **三步**（这就是「模板性」的验收口径）

1. **侦察**（只读）：跑 `m7b28_doubao_recon.py` 的同款探针（Kimi 用 `m7b28_kimi_recon.py`，见
   [网页版协议实测记录 §10](../网页版协议实测记录.md)）→ 拿到 **入口形态 / 选择器 / 网络特征**；
2. **写站点单元**：新建 `ai/upload/sites/site_upload_<站>.cpp`（照 `site_upload_doubao.cpp` 的四个函数），
   在 `site_uploads.h` 加一行声明，在 `upload_registry.cpp` 的 `site_uploads()` 挂上；
3. **落表字段**：`providers.json` 的该条目 `web.upload_adapter`（+ 需要时 `attach_selector` / `upload_accept`）。

> 验收判据：`aiwrite.exe --upload-selftest` 的 **③ 注册表与契约** 组会校验新单元「四个函数指针齐全 +

> **M8-37 之后的语义变化**：两站**不再**因缺字段被判为「登录型条目 → 生成不可用」（⚠️ **但「可运行」≠「结果可信」**：答案侧自动识别**不可靠**，见下方 ⚠️ 与 §9.6 反证）。
> 点「运行」时的真实顺序 = **会话引导 → 图片上传（双证据）→ 注入提示词 → 发送 → 取答案**，
> 其中未回填的选择器由运行期自动识别（结果**只打印**在 Console / 日志 / `steps` 里）。
>
> **为什么回填**（`attach_selector` = **可选兜底**；`answer_selector` = **真机前建议必做**）：
> 1. 声明值**优先**且**稳定** —— 免去每次运行的启发式开销与选错容器的风险；
> 2. 自动识别是**兜底**，站点改版（类名变化）时它比固定选择器更抗变，但**取到哪块容器**以页面为准 —— ⚠️ **实证：取到的可能根本不是回答**（豆包 = `div.bp5-overflow-list`，12 字节）；
> 3. 单站点可跑通后，把 Console 里的指纹粘进 `providers.json` 即可把「猜测」变成「数据」。
>
> **回填方法（一次实跑，4 步；`answer_selector` 强烈建议做）**：
> 1. `aiwrite.exe --web-dom-dump --provider <id>` —— 只读枚举候选 + 建议选择器；
> 2. 在该站点**手动发一条消息**（回答容器只有出过回答才在 DOM 里）；
> 3. `aiwrite.exe --web-adapter-selftest --provider <id>` —— 只读复核各选择器命中数；
> 4. 把命中值写进 `assets/providers.json` 该条目的 `web.answer_selector`（必要时 `input_selector` / `send`）。
>
> 回填完成后：`aiwrite.exe --upload-selftest --provider <id>` 的「生成字段」会变为 **齐全**（`web_login_only` 为 false）。

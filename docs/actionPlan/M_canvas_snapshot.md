## §1 结论摘要（先读这一段）

**一句话**：现在卡，不是"GPU 画不动"，而是**每帧把 85 个节点的全部内容重算、全量提交**（含一批与画面无关的引擎计算）；本文的做法是**把每个节点的"内容"烘焙成各自的高分辨率纹理（卡片快照）**，帧内只贴图 + 由 imgui-node-editor 照常画边框/选中/悬停/连线，从而**在不改变任何交互语义的前提下把每帧成本压到常数级**。

**三条主线**：

1. **公共降载（`CS-01`…`CS-03`）**：可见性剔除 + LOD + 昂贵计算按"图版本号"缓存 —— **不需要快照就能先拿到大部分收益**，且是卡片方案的前置（剔除决定"该烘焙谁"）。
2. **每节点卡片快照（`CS-04`…`CS-08`，方案 A）**：节点内容烘焙成纹理 → 用 `ImDrawList::AddImageQuad` 贴回节点矩形；**尺寸用同一段布局代码实测**（§5.2），**清晰度按缩放档烘焙**（§5.3），**失效用信号表**（§5.6），**内存用 LRU 预算**（§5.7）。
3. **可回退与可观测（`CS-09`…`CS-10`）**：`canvas_render_mode = auto|live|snapshot` 开关 + `[诊断] 画布` 指标行 + 同源尺寸自检。

**为什么不是"整图一张大纹理"**：本工作流节点坐标实测跨度 **7280 × 3300 世界像素**（§2.8），整图一张 RGBA8 纹理 @1.5× ≈ **235 MB**、@2× ≈ **418 MB**（且宽度 15000 已逼近典型 `GL_MAX_TEXTURE_SIZE = 16384`）⇒ 单张巨图**不可行**；而"每节点一张卡片" @1.5× 合计约 **30 MB**、@2× 约 **53 MB**，且**失效粒度细到一个节点**。

| # | 事实 | 位置 |
|---|---|---|
| 1 | `draw_node_canvas()`（画布主函数）内 **对全部节点无条件调用 `draw_node_body(node)`**，随后画全部连线 | `source/src/ui/node_canvas.cpp:1120`（函数）、`:1180`（逐节点调用） |

### 2.4 库侧没有剔除能力

- vendored imgui-node-editor 的 `ImGuiEx::Canvas` **只做 clip rect 变换**：把当前裁剪矩形换算到画布坐标后 `ImGui::PushClipRect(...)` —— `source/third_party/imgui-node-editor/imgui_canvas.cpp:419-478`（`EnterLocalSpace`）。
- 也就是说：**屏幕外的节点，图元照样全部生成**，只是被裁剪掉 —— 裁剪省的是"像素填充"，**不省 CPU 与顶点上传**。
- 结论：要省，必须在**调用方**（`draw_node_canvas()` 的循环里）自己判断"这个节点要不要画"。

内存估算（RGBA8 = 4 字节/像素；**假设单卡 220 × 180 逻辑像素** —— 该假设必须由 `CS-01` 实测替换，见 §5.2）：

| 整图一张 @2× | 15000 × 6960 = **10440 万像素** | **≈ 418 MB**（宽 15000 已逼近典型 `GL_MAX_TEXTURE_SIZE = 16384`） |
| 视口整层 @1.5×（1600×900 逻辑） | 2400 × 1350 = **324 万像素** | **≈ 13 MB** |
| 每节点卡片 @1.5× | 330 × 270 = **8.9 万像素/张** | **≈ 30 MB**（85 张） |
| 每节点卡片 @2× | 440 × 360 = **15.8 万像素/张** | **≈ 53 MB**（85 张） |

## §4 路线对比（A 为主线 · B/C/D 的定位）

| 方案 | 做法 | 内存（85 节点基准图） | 清晰度 | 交互语义 | 工作量 | 判定 |
|---|---|---|---|---|---|---|
| **A 每节点卡片纹理** | 每个节点的**内容**烘焙成一张纹理；帧内 `ImDrawList::AddImageQuad` 贴回节点矩形（**边框 / 选中 / 悬停 / 连线锚点仍由 imgui-node-editor 画**） | @1.5× ≈ **30 MB** · @2× ≈ **53 MB**（LRU 上限可配） | **高**（烘焙到 `ui_scale × 缩放档` 密度，不受屏幕像素上限约束） | **零改动**（节点矩形尺寸不变 ⇒ 命中/框选/拖线/右键菜单行为不变） | 中 | ✅ **主线**（开发者 2026-10-09 拍板） |
| **B 视口整层快照 + 覆盖层** | 静置 ~150 ms 后用 `glReadPixels` 抓可视区 → 纹理；之后每帧只画这张图 + 少量覆盖层；平移/缩放时先用旧图平移显示，静置后重抓 | ≈ **13 MB** | 中（**放大后模糊**，跨缩放档必须重抓） | **需处理**：快照会盖住 ed:: 的悬停/选中高亮 ⇒ 要么失效重抓、要么加覆盖层（z 序问题） | 小 | ⚠️ 备选（`CS-04` 若受阻时的降级实现，**不排期**） |
| **C 全图瓦片快照** | 世界坐标切 2048² 瓦片 + LRU 流式 + 超采样；缩放/平移都靠拼瓦片 | 可控（只留可见瓦片 + 预取一圈） | 高 | 不变（瓦片只是背景层） | 大 | 🟡 可选（将来做**小地图 / 总览**时再上；本文不排期） |
| **D 纯降载（不做快照）** | 视口剔除 + LOD（缩到很小只画标题条）+ 昂贵计算按"图版本号"缓存（§2.3 那张表） | **0** | 不变 | 不变 | 小 | ✅ **公共前置**（`CS-01`…`CS-03`）—— 单独就可能达标（§3.3） |

**为什么 A 能当主线**：

1. **交互语义零改动** —— imgui-node-editor 的命中判定、框选、拖拽、连线锚点都建立在"节点矩形"上，而矩形由我们提交的内容尺寸决定；只要**尺寸一致**（§5.2 的同源布局），把"文字控件"换成"一张图"对它是透明的。
2. **失效粒度细** —— 改一个节点的参数只重烘**一张**卡，不是整屏重抓。
3. **内存线性可控** —— 卡片数 × 单卡尺寸，LRU 预算硬约束（§5.7）。
4. **与"高分辨率"目标一致** —— 卡片可烘焙到 `ui_scale × 缩放档`，**不受当前屏幕像素上限约束**（方案 B 受）。
5. **不做整图** —— §1 的算术：整图 @2× ≈ 418 MB 且宽度逼近纹理上限 ⇒ 不可行。

**B 为什么只当备选**：它的"零新依赖、实现最快"是真的，但 ① 放大后必然模糊（可复用的永远只是"当时的屏幕像素"）；② 覆盖层与 ed:: 的高亮 z 序冲突必须专门处理，否则**交互反馈丢失**（用户会以为"点不动了"）。若 A 的 FBO 路线在本机驱动上受阻，**B 可作为降级实现**（只做实现替换、不改契约）。

**D 为什么必须先做**：剔除决定"该烘焙谁"、该"画谁"（没有剔除，卡片方案只是把"每次都画"变成"每次都贴图"，收益有限）；计算缓存决定"每帧还要不要跑 §2.3 那张表"。三者关系：**D 是地基，A 是上层**。

## §5 主线设计 A：每节点卡片快照

### 5.1 绘制分层（z 序 —— 决定交互反馈会不会被盖住）

| 层 | 谁画 | 内容 | 备注 |
|---|---|---|---|
| 1 | imgui-node-editor | 画布背景 + 网格 | 现状不变 |
| 2 | imgui-node-editor | 连线（links） | 现状不变 |
| 3 | imgui-node-editor | 节点背景板 / 边框 / 选中高亮 / 悬停高亮 | 现状不变（`ed::BeginNode`…`ed::EndNode` 的边框在内容**之后**画） |
| 4 | **我们（卡片快照）** | 节点**内容**：标题、端口行、参数预览、必失败原因、图片缩略图、运行摘要 | 🆕 由"逐控件提交"改为"贴一张图" |
| 5 | 我们（实时覆盖） | 运行中动画（脉冲光环）、拖拽指示等**必须动**的元素 | 🆕 只在需要时叠加（见 §10.1 `CS-R3`：运行中节点强制实时） |

> **关键点**：卡片贴图发生在 `ed::BeginNode()` … `ed::EndNode()` **之内**（层 4），所以 ed:: 的边框/高亮（层 3 的后半）**照常盖在贴图之上** ⇒ **不需要**覆盖层、**不会**丢交互反馈 —— 这正是 A 优于 B 的地方。

### 5.2 尺寸契约（**本方案的第一风险点**）

| 项 | 约定 |
|---|---|
| 问题 | 卡片贴图时要给 ImGui 一个**确定的尺寸**；而节点矩形现在是"提交控件后实测出来的"（`update_content_width()` `node_canvas.cpp:457` + `ed::GetNodeSize`）⇒ 尺寸不一致会**错位**（端口锚点、命中区、连线起点全偏） |
| 做法（同源布局） | 烘焙时**走与实时完全相同的布局代码**（复用 `draw_node_body()` `node_canvas.cpp:596` 的排版分支，只在"要不要真正画像素"上分叉），把**实测出来的内容高度**记进卡片元数据；实时绘制时改提交 `ImGui::Dummy(ImVec2(g_content_width, cached_h))` + 每端口行 `Dummy(kPinDotSize, line_height)` |
| 为什么可行 | 端口行高、标题行高、分隔线都是**常量或由同一批度量得出**；同一段代码在"烘焙"与"占位"两个模式下输出**同一个尺寸**，因此天然一致（**不复制常量**，避免两处维护） |
| 自检 | 扩展既有 `check_uniform_node_width()`（`node_canvas.cpp:990`）为"**尺寸自检**"：每帧抽样比对 `ed::GetNodeSize(node)` 与卡片元数据；**差异 > 1 像素** ⇒ `[诊断]` WARN + 立即让该节点**回落实时绘制**（自愈） |
| 待实测 | "单卡 220 × 180 逻辑像素"是 §2.8 的**假设**；`CS-01` 要打印各类型节点的实测尺寸（含图片卡），并回填本节与 §2.8 的表 |

### 5.3 清晰度契约（**本方案的第二风险点**）

| 项 | 约定 |
|---|---|
| 契约 | 卡片纹理的**像素密度 ≥ 屏幕像素密度**：即 `bake_scale ≥ zoom × ui_scale`（`zoom` = 画布缩放，`ui_scale` = 显示器缩放，§2.7） |
| 档位 | 烘焙档 `B ∈ {1, 1.5, 2, 3}`；取满足契约的**最小档**（`bake_scale = ceil_to_step(zoom × ui_scale)`） |
| 复用 | 缩放**不跨档**时继续用现有纹理（由 ImGui 采样缩放，**可接受**，因为契约仍满足）；**跨档**才重烘 |
| 缩放中 | 缩放/平移**进行中**不重烘（避免拖动时抖动与烘焙风暴）；松手后 150 ms 统一重烘"该档还缺"的可见卡片 |
| 兜底 | 若某节点在当前档的烘焙**失败**（FBO 不完整 / 内存不足）⇒ 该节点**回落实时绘制**（视觉不一致按 `VC-04` 判定，不得静默变糊） |
| 判定 | `VC-04`：在 `100%` 与 `200%` 两档缩放下截图比对"同一节点文字边缘锐度"；**允许**的差异是"无（同档）"或"更清晰（高档）"，**不允许**变糊 |

### 5.4 离屏渲染（FBO 自取指针 + "离屏帧"三条纪律）

**A. GL 入口点自取**（`CS-04` · 新增模块内一次性初始化，失败即整体降级）

| 需要的入口点（约 10 个） | 用途 |
|---|---|
| `glGenFramebuffers` / `glDeleteFramebuffers` / `glBindFramebuffer` | FBO 生命周期与绑定 |
| `glFramebufferTexture2D` / `glCheckFramebufferStatus` | 把卡片纹理挂上 FBO / 校验完整性 |
| `glGenRenderbuffers` / `glBindRenderbuffer` / `glRenderbufferStorage` / `glFramebufferRenderbuffer` | 深度缓冲（如烘焙需要；必要时可省） |
| `glBlitFramebuffer` **或** `glCopyTexSubImage2D` / `glReadPixels`（GL 1.1 已有） | 把渲染结果落进纹理 / 切分成 N 张卡片 |

- 取法：`glfwGetProcAddress("glGenFramebuffers")` → `reinterpret_cast` 到**自定义 typedef**（Windows 的 `GL/gl.h` 只有 GL 1.1，没有这些 typedef）。
- **失败即降级**：任一入口点为 `nullptr` ⇒ 打印一条 `[诊断] 画布` 说明并把 `canvas_render_mode` 视为 `live`（**不静默**，`AI_README.md` §7 第 7 条）。

**B. "离屏帧"三条纪律**（烘焙的实现方式）

| 纪律 | 说明 |
|---|---|
| ① 不调 `ImGui_ImplGlfw_NewFrame()` | 离屏帧**不处理输入**：只 `ImGui::NewFrame()`…`ImGui::Render()`，`io.DeltaTime` 自填（如 `1/60`），`io.DisplaySize` 设为"卡片格子"尺寸 |
| ② 不消费输入 | 离屏帧里不读鼠标/键盘；`io.WantCaptureMouse` 等**只在主帧**使用（否则窗口焦点/拖拽会错乱） |
| ③ 每 `NewFrame()` 必有 `Render()` | 否则 ImGui 断言（Debug 下直接崩）—— 用 RAII 包裹（`CS-04` 的编码要求） |
| ④ 渲染目标 | `glBindFramebuffer(GL_FRAMEBUFFER, fbo)` → 清屏（透明）→ `ImGui_ImplOpenGL3_RenderDrawData(ImGui::GetDrawData())` → 解绑（**恢复默认 FBO**，否则主帧画到离屏里 = 黑屏） |
| ⑤ 进度可控 | 每帧最多烘焙 `K` 张（默认 4）或 `M` 毫秒（默认 4 ms），由 `CS-06` 的调度器控制（避免"首次打开大图一次性烘焙 85 张"造成长时间卡顿） |

> 备选实现（若 FBO 在本机不可用）：把卡片排到**主帧**的一个临时区域再 `glReadPixels` 切分（"滚屏烘焙"）。**代价是烘焙期间画面会抖**，只在 `CS-04` 明确受阻时启用，并登记到本文 §12。

### 5.5 烘焙调度（谁先烘、什么时候烘）

| 规则 | 内容 |
|---|---|
| 只看可见 | 只为"**当前视口内 + 预取边缘 1 屏的 25%**"的节点排队（剔除见 `CS-02`） |
| 优先级 | ① 视口中心的节点 ② 被选中的节点 ③ 其余可见节点 ④ 预取区节点 |
| 时机 | 每帧预算用尽即停（§5.4 ⑤）；缩放/平移**进行中**不烘；松手 150 ms 后批量补齐 |
| 去抖 | 参数快速拖动（键盘连按 / 数值拖拽）⇒ 先打"脏"标记，**最后**统一烘一次（避免每帧重烘同一张卡） |
| 上限 | 队列长度与"每帧张数"都进 `[诊断] 画布`（`cards_baked`），便于判断是否"烘焙赶不上" |

### 5.6 失效信号表（**缓存键 = 决定"这张卡还能不能用"**）

| 信号 | 影响的卡 | 来源 / 依据 |
|---|---|---|
| 图结构或参数变更 | 该节点（改参数）/ 全图（连线变化可能影响"必失败原因"） | 🆕 `EditorState::revision`（见下） |
| 节点状态变更（Idle/Waiting/Running/Done/Error/Skipped） | 该节点 | 引擎状态更新处（`NodeState`） |
| 运行结果摘要变更 | 该节点 | 运行快照 `RunSnapshot` 更新处 |
| 卡片用图变更（参数里的图片路径） | 该节点 | `node_card_image()`（`node_canvas.cpp:572`）的返回值 |
| **图片文件本身变更**（同名同路径但内容变了） | 该节点 | 文件 `mtime` + `size`（照抄 `texture_cache.cpp:44-56` 的键写法） |
| `ui_scale` 变更（跨显示器拖窗口 / 改系统缩放） | 全部 | `app.cpp:430` 的重算点 |
| 缩放档变更（§5.3） | 全部可见 | 画布 `zoom` |
| 主题 / 配色变更 | 全部 | `ui/theme.h` 的颜色常量（当前是编译期常量 ⇒ 实际只在"改代码"时变，但键要留着） |
| 字体 / 字号变更 | 全部 | `app.cpp:435` 附近 |

**`EditorState::revision`（`CS-03` 新增）**：`source/include/ui/editor_state.h` 的 `EditorState`（`:22`）当前**没有**任何 `revision` / `dirty` 计数（已核实）⇒ 新增一个 `std::uint64_t revision`，在**会改变画面内容**的操作后自增：加/删节点、加/删连线、改参数、改标题、粘贴、打开工作流、撤销/重做。用途有两个（**一物两用，别再各造一套**）：① 卡片失效（本节）；② §2.3 昂贵计算缓存的键（`CS-03`）。

### 5.7 预算与淘汰（LRU + 可见钉住）

| 项 | 约定 |
|---|---|
| 上限 | `[ui] canvas_card_cache_mb`（默认 **128 MB**）；实占用进 `[诊断] 画布` 的 `cards_mb` |
| 淘汰 | 照抄 `texture_cache.cpp:80-83` 的 LRU 写法：超预算时淘汰**最久未使用**的卡片 |
| 钉住 | 当前**可见**与**被选中**的卡片**不淘汰**（否则会出现"贴图时正好被淘汰"的抖动） |
| 淘汰后 | 该节点**立即回落实时绘制**（本帧就有正确画面），下一轮再烘 |
| 硬失败 | 单张卡片尺寸超过预算上限（例如 3× 档的超高卡片）⇒ 该节点固定用实时绘制（记 `[诊断]` WARN，不静默） |

### 5.8 LOD 与降级阶梯

| 档位 | 触发 | 画什么 |
|---|---|---|
| 全细节（默认） | `zoom ≥ canvas_lod_zoom` | 卡片快照（本方案主线） |
| 标题条 | `zoom < canvas_lod_zoom`（默认 0.6） | 只画"分类色条 + 标题 + 状态点"，不烘卡片（远看本来就读不清字） |
| 实时兜底 | 烘焙失败 / 尺寸自检不一致 / 处于动画期（§10） | 该节点走 2026-10-09 的实时绘制路径（**逐节点粒度**，不是全局） |

### 5.9 回退开关（`AC-05` 的依托）

| 键 / 行为 | 语义 |
|---|---|
| `[ui] canvas_render_mode = "auto"`（默认） | 自动：具备条件就用卡片快照，否则实时 |
| `= "live"` | **强制实时**：与 2026-10-09 行为一致（用于 A/B 对照、故障回退、真机回归） |
| `= "snapshot"` | 强制快照：用于验证快照路径本身（缺 FBO 时**报错提示**而不是静默回落） |
| 热切换 | 改配置后**当帧生效**（不需要重启）；切换时释放 / 重建缓存由 `CS-08` 负责 |

## §10 风险与不做清单

### 10.1 风险（含默认处置）

| 编号 | 风险 | 默认处置 |
|---|---|---|
| `CS-R1` | **尺寸漂移**（卡片高度 ≠ 实际布局高度 ⇒ 端口/连线错位）**最高风险** | 同源布局（§5.2）+ 尺寸自检（差异 > 1 像素 ⇒ WARN + **逐节点**回落实时自愈） |
| `CS-R2` | **清晰度下降**（放大后文字糊） | 档位烘焙 + 契约判定（§5.3）+ `VC-04` |
| `CS-R3` | **运行中动画与快照冲突**（`ui.running_animation` 的脉冲光环本身每帧在变） | **默认口径：运行中的节点强制实时绘制**（逐节点粒度，其余节点仍走快照）。若将来要"快照也要动画" ⇒ **开新条目**（本文不排期、不预留实现） |
| `CS-R4` | FBO / 驱动差异（自取指针失败、FBO 不完整） | 自取失败即整体降级（`[诊断]` 明说）；`snapshot` 模式报错**不静默** |
| `CS-R5` | **烘焙风暴**（打开大图时一次性烘 85 张 ⇒ 卡顿） | 每帧预算 + 优先级 + 去抖（§5.4 ⑤ / §5.5） |
| `CS-R6` | 内存超预算 / 单片过大 | LRU + 钉住 + 单片超限即固定实时（§5.7） |
| `CS-R7` | DPI 变化（跨显示器拖动 / 改系统缩放） | `ui_scale` 信号全清重建（§5.6） |
| `CS-R8` | 误伤 M7 图片冻结区（`I17`） | 图片**只读**复用 `image_decode` 与 `texture_cache` 的键写法，**不改**解码路径 |
| `CS-R9` | 与后续功能打架（例如将来做"节点内嵌视频/动画预览"） | 靠"逐节点回落实时"的粒度隔离：任何"必须每帧变"的节点都退回实时，不进快照 |

### 10.2 不做清单（本轮明确不做 · 留痕）

| # | 不做 | 理由 / 现行指向 |
|---|---|---|
| 1 | 不改 `source/third_party/imgui-node-editor/**` | `AI_README.md` §7 第 4 条红线 |
| 2 | 不引入 `glew` / `glad` 或任何新第三方依赖 | 离屏入口点自取即可（§5.4 A）；新依赖要走依赖变更流程 |
| 3 | 不把画布快照写进 `~/.brain-ai/snapshots` | 该目录是**运行快照** `RunSnapshot` 的（`utils/paths.*`）；术语区分见 [../变量术语对照表.md](../变量术语对照表.md) §12.2 |
| 4 | 不做"整图一张大纹理" | §1 / §2.8 的算术：@2× ≈ 418 MB，宽度逼近 `GL_MAX_TEXTURE_SIZE` |

| 7 | 不改既有 CLI 行为 | 守住 `I20`（新开关只做加法） |
| 8 | **本轮（2026-10-09 · v2）不做 `CS-04`…`CS-10`（卡片快照 / FBO 烘焙）** | **实测已达标**：§3.3 第一行判据（≈60 FPS）+ §2.9 改后 `FPS 59~60`、CPU 帧预算 ≈ 4.5 ms/帧 ⇒ 快照的收益不再是"能不能跑动"，而是"省那几个 ms"（**收益/风险比在 `CS-R1` 尺寸漂移面前不划算**）。**现行指向**：若要继续，先做 `CS-02`（图版本号缓存）与 `CS-03`（视口剔除）；`CS-04`+ 保持"计划中"，不排期 |
| 9 | **本轮不把纹理缓存策略做成离线断言** | 现有实现依赖 GL 上下文（`glGenTextures` / `glTexImage2D`）⇒ 断言需先把策略与 GL 拆开（属 `CS-05` 的"纯逻辑部分"思路）。**登记为待做**（§11 待做 7），**不为凑测试而硬拆** |

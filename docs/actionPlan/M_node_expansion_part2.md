#### 4.3.2 分类结构（L2-A）

**两层结构**：

```
辅助功能（顶层分类 · 新建 · id `Auxiliary` · 显示名「辅助功能」）
  └─ 文本处理（子分类 · 新建 · id `TextProcess` · 显示名「文本处理」）
       ├─ TextSplit   文本分块
       ├─ TextExtract 文本提取
       ├─ TextClean   文本清理
       ├─ TextReplace 文本替换
       ├─ TextStats   文本统计
       └─ TextDiff    文本对比
```

**与现有 5 分类的关系**：

| 分类 | 现有节点 | 性质 |
|---|---|---|
| 输入 | `N-01 TextInput` · `N-02 ImageInput` | 内容进入 |
| 处理 | `N-03 PromptTemplate` · `N-04 TextMerge` | **流程性**操作（模板 / 合并） |
| 配置 | `N-05 ProviderConfig` | 提供商配置 |
| 推理 | `N-06 LLMGenerate` · `N-07 VLMGenerate` | AI 调用 |
| 输出 | `N-08 TextOutput` | 成品离开 |
| **辅助功能**（新） | — | **辅助性操作容器** |
| └ **文本处理**（新） | 6 个 B 档节点 | **原子文本操作** |

**分类判据**：

| 分类 | 职责 | 输入/输出 |
|---|---|---|
| **处理**（现有） | **流程性**：多路输入组装/合并为一路 | **不对称**（多变一、或模板+变量→文本） |
| **辅助功能 → 文本处理**（新） | **原子性**：对单路文本做单一变换 | **对称**（一入一出，或一入多出） |

**实现方式（L2-A-3 = B）**：**伪两层，只改 UI**。
- 顶层「辅助功能」下以**视觉分组**呈现「文本处理」子分类。
- **不改** `NodeRegistry` 架构；只改 `node_library.cpp` 渲染。
- 未来若有「图片处理」「文件处理」等，可继续加视觉分组。

## §5 代价边界：哪些想法**根本不属于「节点扩展」**

以下三项**留在本文**（`NE-Q3`），**与 L1~L4 并列展示，但不排期、不立任务号**；将来立项流程 = **将来再定**（`G-2`）。

| 想法 | 为什么不是「加节点」 | 需要的改动 | 已登记状态 |
|---|---|---|---|
| **条件分支** | 需要「**节点是否执行由上游值决定**」的**图级**语义 | 执行器调度（跳过 / 激活）+ 校验（悬空分支）+ UI（分支表示） | §19.1 延后 · 不排期 |
| **循环 / 批量** | 需要「**同一节点重复执行**」或「子图重复执行」 | 执行器支持**多轮遍历**与值覆盖 | §19.1 延后 · 不排期 |
| **子工作流** | 需要「**图套图**」：工作流成为可被调用的单元 | 契约新增「工作流实例」概念 + 参数映射 + 递归 / 深度限制 | §19.1 延后 · 不排期 |

**引擎侧现状（[../../source/engine/include/executor.h](../../source/engine/include/executor.h) 第 6–13 行 · 设计原文）**：

- 「单线程分帧：`tick()` 每帧推进**一个节点**（UI 调用）；无 UI 场景用 `runToCompletion()`」
- 「状态机：`Waiting → Running → Done / Error`；失败节点的下游标 `Skipped`，**无关分支继续**（§10.4）」
- 「运行态**值**只存在于 `Executor`（`NodeOutputs`），**不进入 Graph** —— Graph 是「文档」」

⇒ 三条合起来说明：**现有执行模型是「静态图 + 一次推进」**；上表三项都要求「**控制流**」能力，属**执行引擎语义变更（v2 量级）**。

> **口径结论（`NE-Q3` 已答 · 2026-10-12）**：**留在本文**（不单列 v2 议题）；**将来立项流程 = 将来再定**（`G-2` = C）。

## 2. 端点（均为 `/api/v0/`）

| 端点 | 说明 |
| --- | --- |
| `POST /chat/create_pow_challenge` | 取 PoW 挑战，body `{"target_path":"/api/v0/chat/completion"}` |
| `POST /chat/completion` | 生成（SSE 流式），body 需 `chat_session_id`(UUID) / `parent_message_id` / `model_type` / `prompt` / `ref_file_ids` / `thinking_enabled` / `search_enabled` |
| `GET  /chat_session/fetch_page` | 会话列表：`data.biz_data.chat_sessions[].{id,seq_id,title,current_message_id,model_type,agent}` |

`chat_session_id` 为 **UUID 字符串**（传 `null` 会得到 `HTTP 422 … expected a UUID string`）。

## 3. PoW（DeepSeekHashV1）—— 已定位，尚未在 C++ 复现

挑战响应形态：

```json
{"code":0,"data":{"biz_data":{"challenge":{
  "algorithm":"DeepSeekHashV1","challenge":"<64hex>","salt":"<hex>",
  "signature":"<64hex>","difficulty":144000,"expire_at":<ms>,
  "expire_after":300000,"target_path":"/api/v0/chat/completion"}}}}
```

**请求头格式（官方实现，与我们的 C++ 实现一致）**——取自主包 `static/main.*.js`：

```js
["X-DS-PoW-Response", base64(JSON.stringify({
  algorithm, challenge, salt, answer /*int*/, signature, target_path
}))]
// 另有访客版头：["X-DS-Guest-PoW-Response", base64(JSON.stringify({salt, answer}))]
```

**求解逻辑**（取自 PoW worker `static/76608.<hash>.js`）：

```js
let prefix = `${salt}_${expireAt}_`;                 // expireAt = expire_at（毫秒）
for (let i = 0; i < difficulty; i++)                 // difficulty = 144000 = 搜索空间
    if (SHA3(prefix + String(i)) === challenge) return i;   // challenge 即目标哈希，answer = i
```

**关键结论（实测）**：worker 用的哈希**不是 NIST SHA3-256，也不是 Keccak-256**。
指纹测试（在官方 worker 内比对明文 `a_b_0` 的 i=0 摘要）：

* `sha3_256("a_b_0")` = `ec87c100…cc1234` → 不命中
* `keccak256("a_b_0")` = `0fd7245c…1e1aa6` → 不命中
* ⇒ 其 sponge 为**自定义变体**（源码中 Keccak-f 轮循环自 `i=1` 起，省略第 0 轮常量）

因此 `ai/web_pow.cpp` 目前的 C++ 求解器**会走不到命中分支**（服务端返回 `{"code":40301,"msg":"INVALID_POW_RESPONSE"}`）。

### 两条可选落地路线

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A（已采用 ✅）** | 在隐藏登录窗口里用**官方 worker** 求解：`ExecuteScript` → 取回 worker 源码 → `Blob` → `Worker` → 返回 `answer` | 已实测可用（138229 / 90885 / 18510…），发版自适应、零逆向风险；实现见 `web::solve_pow_via_page()` |
| B | 忠实移植其 sponge（差异点已定位：轮常量从 `i=1` 开始）到 C++/OpenSSL 变体 | 纯 C++，但需逐位对齐且随前端更新会再失效；当前仅作为页面内求解失败时的兜底（`ai/web_pow.cpp`，通常不会命中） |

方案 A 的实现要点（`src/web/webview_host.cpp`）：

1. `ensure_session()`：没有凭证时离屏起登录窗口并等一次协议探测（拿 Cookie + userToken）；
2. 注入挑战 JSON → 注入求解脚本（两段式：结果写入 `window.__aiwritePowResult`，`WM_TIMER` 轮询取回，
   规避部分运行时 `ExecuteScript` 不等待 Promise）；
3. 脚本内**运行时发现** worker chunk：找 `main.*.js` → 正则 `new Worker(new URL(…u\((\d+)\)` 取模块 id →
   在 chunk 表中取 hash → 用「主包 URL 换文件名」拼 worker URL → `fetch` 源码 → `Blob` → `Worker`；
   另有「上次实测 URL」兜底；
4. 跨线程同步：主线程 `PostMessage(WM_APP+2)` → 窗口线程 `ExecuteScript` → 条件变量回传 answer（默认 90s 超时）。

## 5. SSE 与正文解析

`POST /chat/completion` 返回 `text/event-stream`，逐行 `data: {json}`；正文可能为
`{"p":"response/fragments/-1/content","v":"文本"}` 或 `{"content":"文本"}` 等形态。
`ai/deepseek_web_client.cpp` 已实现通用提取（`p` 含 `content` 取 `v`、递归取 `content`/`text`），
并把**原始前 12 行**放进 `WebChatResult.raw_head`，便于前端格式变化时快速对齐。
